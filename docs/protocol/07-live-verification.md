## 3. 被证伪 / 被更正的结论

诚实起见，逐条列出早期版本中**说错或说重了**的地方。

### 3.1 ❌→✅ 「接收帧前 2 字节是 CRC」——**证伪**

早期版本写「⚠️ 疑为 CRC-16」。实测两个独立样本都是 `00 00`，
而按 `payload[2..]` 算出的 CRC-16/CCITT-FALSE 是 `0x7499`、`0x969E`，
**不符**。结论：这两字节恒为 0，不是 CRC；新客户端也不校验。

（老的 `KVMUtil.doDivi` 确实在该位置校验 CRC，所以是历史遗留字段。）

### 3.2 ❌→✅ 「BMC 会校验客户端帧的 CRC」——**证伪**

把 `GET_SUITE` 的 CRC 字段改成 `0000`，BMC **仍然正常应答**（重复 3 次一致）。
所以至少对 `GET_SUITE`，BMC 不校验 CRC。

### 3.3 ❌→✅ 「BMC 会校验 codeKey」——**证伪**

把 codeKey 改成 `0`、乃至全部取反，`GET_SUITE` 仍被应答。
**套件协商确实是免认证的**（这一点早期判断正确，现在有了直接证据）。

### 3.4 ✅→⚠️ 「实测抓到视频帧率命令 0x1C」——**过度声称，已修正**

早期版本写「✅ 实测抓包：`...521f1c23`」。实际上那只是**本地发送日志**：
`CONNECT_BLADE` 被拒后 socket 很快关闭，`0x1C` 与 `0x24` 的发送与
`socket closed` 存在**竞态**（两次运行的日志顺序都不一样），
**不能证明 BMC 收到了它们**。已在 03 章与 04 章标注。

### 3.5 ✅ 早期判断正确的部分

- 两个方向帧格式不对称 —— 正确，且现由「帧完美贴合」强证据支持
- `packLenght / 220 + 1` 的子包切分 —— 正确
- CRC 是 CRC-16/CCITT-FALSE（poly 0x1021, init 0）—— 正确
- `decrykey` 拆成 `user_key`/`user_iv` —— 正确
- 连接后 BMC 下发 48 字节 `kvm_key` 材料 —— 正确

### 3.6 早期「未确认项」的落定

| 早期未定项 | 现在 |
|---|---|
| 帧头子包是否加密 | **不加密**。`DrawThread.java:140` 的 `if / else if` 使序号 0 的子包跳过解密分支 |
| 重组缓冲是否有尾部零填充 | **没有**。`packLenght` 不含帧头包，缓冲恰好 `packLenght+1` |
| 块流起始偏移 | **索引 1**（`data[0]` = 差分标志） |
| 块流是否稠密（覆盖所有块） | **是**。130 块全部出现，未变化区域用复制块表示 |
| JPEG 块长度上限 | **不受 250 限制**。实测单块扫描数据 600 字节；250 只约束子包 |
| 默认 DQT 档 | **70**（索引 6），不是字段初值 4 |

## 4. 重要运行性发现

### 4.1 JNLP 会话**一次性**

实测：同一个新 JNLP 第一次连接成功（`CONNECT_STATE = 0`，视频正常）；
断开后**再连就被拒**（`CONNECT_STATE = 3` 并立即断链）。

**含义**：每次要抓包都必须**重新下载 JNLP**（浏览器里重新点一次远程控制台）。
一个 JNLP = 一次控制台会话。

> 这也解释了为什么早期两个 JNLP 都返回状态 3 —— 它们不只是「过期」，
> 更可能是**已经被用过**。

### 4.2 BMC 在握手后会主动推 4 个帧

```
rx 0x40 dlen=52    ← 48 字节 kvm_key 材料
rx 0x40 dlen=132   ← 128 字节重连密钥
rx 0x28 dlen=8     ← DQT 档位 = 70
rx 0x25 dlen=8     ← 鼠标模式
```

注意 **`0x40` 连发两次**（48B + 128B），客户端据此分别设置
`kvm_key` 与 `reconnKey`。早期文档只描述了 48B 分支。

### 4.3 `0x25`（鼠标模式）的字段不是刀片号

实测收到 `00 00 25 02 01 00 00 00`：`payload[3] = 0x02`、`payload[4] = 0x01`。
我们请求的是模式 2，BMC 上报模式 1（同步/绝对）。

所以 **`payload[3]` 不总是刀片号**（在 `0x02`/`0x08`/`0x43` 里是 0，
在 `0x25` 里是 2）。客户端只读 `payload[4]`。⚠️ `payload[3]` 的确切语义未定。

### 4.4 客户端帧必须整帧一次 write

实测把一帧拆成两次 write（间隔 300/800ms）后 BMC **无应答**；
整帧一次 write 则每次都正常。⚠️ 样本较少，但实现时应**一帧一次 write**，
不要依赖 BMC 重组 TCP 分片。

## 5. 复现步骤

```bash
# 1) 浏览器登录 iBMC，点一次「远程控制台」，得到新 JNLP（一次性！）
# 2) 握手 + 抓流（写文件，含 0x40 密钥材料）
node tools/kvm-live.mjs <新jnlp> /tmp/kvmlive 20000
# 3) 离线解析：派生 kvm_key、重组子包、导出块流
node tools/kvm-analyze.mjs /tmp/kvmlive/server.bin <新jnlp> /tmp/kvmanalyze
# 4) 走块流，校验字节是否精确消耗
node tools/kvm-blocks.mjs /tmp/kvmanalyze/frame-2.bin
# 5) 合成 JPEG 头并渲染出画面
python3 tools/kvm-render.py /tmp/kvmanalyze/frame-2.bin \
        /tmp/kvmanalyze/frame-2.blocks.json /tmp/kvmanalyze/frame-2.png 6
```

工具都在 [`tools/`](tools/)。第 3~5 步需要 `python3` + `Pillow`。

## 7. JAR 二进制一致性核对

本文档的所有源码结论都基于反编译，因此必须确认**反编译的 JAR 就是设备在跑的那个**。
核对三份副本的 SHA-256：

| 来源 | SHA-256 |
|---|---|
| icedtea-web 缓存（OpenWebStart 实际下载并运行的）<br>`~/.cache/icedtea-web/cache/0/1/vconsole1555733171728880755.jar` | `3f5d204c0f027a0efc9a42998d1af61560f8a77db0a48e0e395f1bf6cd61d5b5` |
| 反编译所用的副本<br>`work/kvm-vconsole.jar` | `3f5d204c0f027a0efc9a42998d1af61560f8a77db0a48e0e395f1bf6cd61d5b5` |
| **从 BMC 实时拉取**<br>`https://192.168.1.100/bmc/pages/jar/vconsole1555733171728880755.jar` | `3f5d204c0f027a0efc9a42998d1af61560f8a77db0a48e0e395f1bf6cd61d5b5` |

**三份完全一致**（1869731 字节）。所以：

- 反编译源码与该设备当前运行的固件**完全对应**，不存在版本漂移；
- 对于**未能实测**的部分（RLE 块、VMM 通道），源码结论的可信度取决于
  代码本身是否有歧义 —— 已在 [03 章 §9](03-video-channel.md) 与
  [05 章](05-virtual-media.md) 标注。

> 注：`/bmc/pages/jar/` 下的 JAR **不需要认证**即可下载（HTTP 200）。
> 这本身不算漏洞（客户端代码总是可获取的），但意味着可以离线核对固件版本。
